# Office dashboard basics

Current Reception/Queue behavior is documented in [RECEPTION_UNIFIED_QUEUE.md](RECEPTION_UNIFIED_QUEUE.md). That phase supersedes the former location-partitioned/shift-backed queue described in the historical notes below.

Routes: /office/dashboard, /office/drivers, /office/queue, /office/vehicles, /office/orders. Customers, reports and settings are explicit placeholders. Existing office API login (tenant slug, username, password), with an in-memory token shared across office navigation. Reload requires sign-in again.

Uses existing API, Driver/Vehicle models, tenant filters, composite foreign keys and reception shifts/queue. Migration 20260927151823_OfficeFleetBasics adds phone/activation and vehicle metadata; existing vehicles become ACTIVE and existing entities stay enabled. No driver application account is activated when creating an office driver record.

Office GET requires rides.read; writes require rides.write (existing dispatcher scope). Server validates cross-office references, duplicate plate, year, phone and active shift restrictions. End an active shift before disabling or reassigning its resources. Driver vehicle links are managed in the driver profile and vehicle editor, with dated DriverVehicleAssignment history and actor. Driver.currentVehicleId is the authoritative current association; historical Vehicle.driverId is not a current assignment indicator.

DriverProfilesAndQueueLocations adds the full editable profile, SUSPENDED state, assignment history and tenant-owned QueueLocation. Existing queue entries retain their entry times and receive a location named from their tenant, with positions starting at 1. Historical assignment times unavailable before this migration are explicitly marked unknown in the recovered history notes.

The queue page manages location names/activation/order and adds drivers after selecting a location. Search uses local phone, name, identity or current plate. A driver can occupy only one queue; transfer requires confirmation and an expected source location. Add/move/remove operations are serialized with the existing tenant lock. Reorder/transfer retain entry times; removal renumbers only that location. Assigning a request preserves queue membership/position/time and marks it BUSY. No automatic rotation policy is introduced. Reception has the same location-specific queue, searchable picker and drag assignment.

DriverContactData separates local phone from WhatsApp metadata. The API exposes phoneLocal (with legacy phone alias backed by the existing Phone column); saves require a leading zero and reject country codes. Migration converts existing +970/+972 driver numbers to local form without changing customer phones. whatsappPhone stores a separate local number, whatsappCountryCode is +970/+972, and hasWhatsApp/whatsappEnabled default false. DriverContact.WhatsAppRecipient prepares an international recipient only when explicitly called and never mutates phoneLocal. No external sender is implemented. Office.OfficeWhatsAppNumber is tenant-scoped and editable in the driver's page collapsed office-number section; saving it does not configure an external service. These fields prepare for future ride details, licence alerts, administrative and bulk messages.

Driver address is an unrestricted manual textarea and PostgreSQL text, without GPS or silent truncation. Normal HTTP request size limits still apply. License dates are editable with a simple expiry warning. Blank optional birth/license/hire dates persist as null.

Dashboard counts use the API business day in Asia/Jerusalem, real reception orders and active assignments. Refresh is every three seconds. Search is local to the authenticated office dataset. No external map, GPS, bridge, tunnel, WhatsApp or iCall changes were made.
