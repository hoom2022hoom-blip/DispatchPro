# تكسي نابلس والمهندس — مراحل التنفيذ

## إدارة المكتب والتقارير — 2026-09-29

- الموجود المحفوظ: تقارير السائق والزبون ببحث الخادم والفترات والتفاصيل؛ إدارة مواقع الدور؛ صلاحيات متعددة المكاتب؛ جميع تكاملات المكالمات والاستقبال دون تعديل.
- اكتملت واجهة `/office/settings`: إنشاء مستخدم، تغيير دوره وتفعيله، إنشاء الأدوار وتعديل صلاحياتها، إعداد اسم المكتب والمنطقة الزمنية، ورابط إدارة المواقع القائمة. صلاحيات الخادم هي المرجع؛ لا يمكن للمستخدم تعطيل نفسه أو سحب صلاحية إدارة المستخدمين من دوره.
- تقرير الطلبات يستعلم من PostgreSQL بصفحات 50 سجلًا وفلاتر التاريخ والحالة والمصدر والبحث، مع إجماليات للفترة وتجميع الحالة والمصدر والسائق والمنطقة. لا يعتمد التقرير على نافذة بيانات الاستقبال المحمّلة.
- طباعة وتصدير CSV للصفحة الحالية في تقارير الطلبات والسائقين والزبائن، مع ترميز المحتوى والحماية من صيغ الجداول. التصدير الشامل وPDF/Excel مؤجلان.
- أساس التنبيهات الداخلية يعرض آخر 50 حدثًا من AuditLog للمكتب بصلاحية `audit.read`، مع تحديث يدوي وقراءة محفوظة لجلسة المستخدم والمكتب. لا Push أو SMS أو إرسال خارجي.
- لا migrations أو استيراد أو تعديلات Auth أو تشغيل للمرحلة المحمولة. الإضافات تحتاج إصدار API المحدث عند نشرها؛ لم تتم إعادة تشغيل خدمة المكتب العاملة أثناء اختبارات هذه المرحلة.
- التالي حسب الخطة: مرحلة تطبيقات السائق والزبون والاتصال اللحظي، وتبدأ فقط بتكليف لاحق.

## متابعة ربط الاستقبال — 2026-09-27

نُفّذ ربط `ReceptionBackend` الحالي بالـAPI مع قراءة وكتابة موحدة في وضع API اختياري، وإعادة استخدام جدول الاستقبال والنماذج والدور والسحب والإفلات. أُضيف عامل Node مستقل يقرأ سجل المكالمات الدائم دون متصفح، مع إعادة المحاولة وإقرار معالجة لكل مكتب، وmigrations لجداول التوافق والترقيم الذري وحماية التعديلات. تكاملات iCall/WhatsApp والشبكة والموفر القديم محفوظة. بيانات الاستقبال متوافقة مع النموذج القديم وليست ترحيلًا تلقائيًا لكيانات الرحلات المحمولة. التفاصيل والتشغيل والاختبارات في [دليل ربط الاستقبال](../backend/RECEPTION_BRIDGE.md).

هذه المتابعة تُنجز خطوة ربط موفر الاستقبال والعامل المذكورة أدناه؛ لم يبدأ Flutter أو تصميم لوحة جديد أو ترحيل بيانات فعلية.

## تحديث المرحلة الأولى — 2026-09-27 (الحالة الأحدث)

### Audit للموجود فعليًا
- الفرع `taxi-nablus-development`؛ توجد تعديلات محلية سابقة كثيرة محفوظة دون حذف أو reset.
- Next.js 15 / React / TypeScript؛ لوحة استقبال عربية، ترتيب وسحب السائقين، ورديات، ترقيم يومي، خرائط MapLibre/Traccar، صفحات السائق والإدارة.
- طبقة `ReceptionBackend` بموفري Firebase وIndexedDB/Dexie. لم يُغيّر اختيار الموفر.
- استقبال مكالمات `/api/calls` مع حماية ومقاومة التكرار وسجل محلي؛ iCall UDP adapter؛ بوابة LAN؛ مشروع Android OfficeCalls الذي يلتقط إشعارات WhatsApp ويحفظ دورة المكالمة. هذه ليست تطبيقات الزبون والسائق المطلوبة مستقبلًا.
- قبل هذه المرحلة: ASP.NET Core كان يحتوي health endpoints فقط؛ ملف PostgreSQL سابق للاستقبال دون multi-tenancy أو مصادقة أو محرك تسعير.
- PostgreSQL 18 موجود ضمن Program Files ولكنه خارج PATH. الخدمة القائمة لم تُعدّل. اختُبرت المرحلة على نسخة محلية معزولة PostgreSQL 18.6 وPostGIS 3.6.2 ضمن `.tools`.

### ما نُفّذ
- توسيع API نفسه داخل `backend/DispatchPro.Api` بوحدات Domain / Infrastructure / Services / Endpoints؛ دون مشروع منتج بديل أو Flutter أو تعديل تصميم اللوحة.
- كل الكيانات المطلوبة: Tenant, Office, User, Role, Permission, Customer, Driver, Vehicle, VehicleClass, RideRequest, Ride, RideStatus, DriverStatus, FeatureFlag, AuditLog, PricingProfile, PricingRule, FixedRoutePrice, ZonePrice, ServiceSurcharge, RidePrice, PriceAdjustment.
- PostgreSQL/PostGIS عبر EF Core/Npgsql، migrations فعلية وقيود علاقات مركبة للمكتب وفهرس يمنع رحلتين نشطتين للسائق؛ تشغيل migrations صريح لا تلقائي.
- JWT وتجزئة كلمات المرور؛ صلاحيات ديناميكية لكل مكتب؛ tenant من token الموثّق فقط؛ مرشحات استعلام وحماية كتابة وعلاقات تمنع الربط عبر المكاتب.
- توحيد الهاتف الفلسطيني بصيغتي الطلب إلى +970؛ اسم كامل دون حقل هوية؛ OTP abstraction تعيد عدم الجاهزية حتى ربط مزود حقيقي.
- تسعير Manual / FixedRoute / GpsMeter / Hybrid مع الليل/النهار والمنطقة وفئة السيارة والخدمات؛ تقدير وحساب ونهائي وتعديل موثّق بسبب وهوية الموظف؛ أعلام ميزات لكل مكتب.
- endpoints للحسابات والأدوار والصلاحيات والمكاتب والسائقين والسيارات والعملاء والطلبات والرحلات والأسعار والإعدادات والسجل؛ حجب بيانات الزبون عن السائق قبل القبول؛ فحص تعارض الإصدارات عند تغيير الرحلة والسعر.
- Seed قابل للتخصيص لمكاتب مستقلة، دون اسم مكتب أو كلمة مرور ثابتين. البيانات الحقيقية لم تُرحّل.

### ما يُحفظ وما يُدمج لاحقًا
- يُحفظ: iCall وWhatsApp وOfficeCalls وكل استقبال المكالمات، شبكة المكتب، Firebase/IndexedDB، ترقيم الطلبات والدور والتعديلات السابقة.
- المرحلة التالية: موفر ASP.NET لـReceptionBackend، worker استقبال مستقل عن المتصفح، event idempotency وترقيم يومي داخل معاملة؛ اختبارات تكافؤ قبل تحويل أي مكتب.
- لاحقًا: OTP SMS فعلي وتسجيل زبون عام، Flutter Android/iOS للزبون والسائق، SignalR للدردشة والموقع، إشعارات واتصال، تقارير PDF/Excel، دفع، جدولة وتوزيع متقدم، نسخ احتياطي واسترجاع ومراقبة إنتاج.
- الأساس الحالي لا يحسب المسافة من بث GPS مباشر؛ يستقبل مدخلات عداد من موظف مخوّل. تخزين حدود PostGIS متاح بصيغة WKT؛ اختيار المنطقة تلقائيًا لاحقًا. تعريف أعلام الدفع والدردشة وغيرها لا يعني تنفيذ خدماتها.

## المعمارية
- الحالي: Next.js/TypeScript وFirebase، مع مكونات Traccar وDexie موجودة.
- المستهدف تدريجيًا: ASP.NET Core Web API، PostgreSQL/PostGIS، SignalR.
- تطبيقات Flutter للسائق والزبون لاحقًا؛ خرائط MapLibre/OpenStreetMap.
- فصل استقبال المكالمات عن الجهاز عبر adapters؛ منع التكرار باستخدام eventId.

## المراحل التالية
1. تم: استقبال عربي RTL، شريط آخر مكالمة للمعلومات، حفظ المصدر والهاتف واسم الزبون، جدول يومي قابل للبحث والتعديل، الحالات التسع واختيار الوردية والسيارة. سعر اختياري وموعد بتاريخ ووقت. فشل الحفظ يبقي المدخلات، ولا تتكرر إضافة الرسوم عند التعديل.
2. تم: نافذة الدور، إضافة/إخراج/بحث/ترتيب وسحب السائق إلى الطلب، اختيار سريع، منع ازدواج التعيين وإخراج السائق من الدور عند التعيين. إعادة دخول الدور صريحة بعد انتهاء الطلب.
3. تم: endpoint محلي دائم للمصادر الأربع ومرسل adapter جاهز. توصيل WhatsApp السابق وجهاز iCall نفسه يحتاج مسار الكود وبروتوكول الجهاز.
4. جارٍ: نقل البيانات تدريجيًا عبر واجهة backend موحدة مع توافق البيانات الحالية. أُضيفت `ReceptionBackend` وربطت لوحة المكتب بها للحفظ والترقيم وتغيير الدور والاستقبال التلقائي، مع providers محلي وFirestore والمحافظة على المعاملات الحالية. بعد نجاح اختبارات الاستقبال أُضيف أساس ASP.NET Core مستقل داخل `backend/` مع health endpoints ومخطط PostgreSQL وCompose. التالي: اختبار PostgreSQL وربط provider والمصادقة، ثم توحيد اشتراكات القراءة؛ لا ترحيل فعلي حتى جاهزية الخادم.
5. تطبيقات السائق والزبون والمراقبة؛ offline queue وretry وidempotency.

لا نشر ولا ترحيل بيانات حقيقية في هذه المرحلة. إعداد Firebase Admin غير موجود محليًا، لذا وظائفه الخلفية غير مفعلة.

## حدود المرحلة المحلية
- بيانات الحساب التجريبي في IndexedDB منفصلة عن Firebase وطابور مزامنة الإنتاج.
- الترقيم محفوظ في `orderDay/orderNumber` حسب يوم القدس، يبدأ من 1 يوميًا. تخصيص ذري عبر Dexie محليًا وFirestore للمستخدم الفعلي. التعديل والفرز لا يغيّرانه؛ ترقية الطلبات السابقة دون حذفها.
- نموذج الطلب يحتفظ بمعرّف المحاولة لتفادي إنشاء طلب ثانٍ عند إعادة الحفظ، وواجهة الدور تتحدث بين تبويبات المتصفح.
- حالات التخزين القديمة محفوظة: pending=NEW، waiting=WAITING، assigned=ASSIGNED، driver-accepted=DRIVER_ACCEPTED، driver-arriving=DRIVER_ARRIVING، arrived=ARRIVED، in-progress=IN_TRIP، completed=COMPLETED، cancelled=CANCELLED.
- إحداثيات النموذج التجريبية الحالية ليست مواقع زبائن فعلية. تحديد المواقع وربط الزبائن وعناوينهم لاحقًا.
- الاختبارات: `npm run test`؛ تشمل حدود اليوم، الترقيم المتزامن، ترقية IndexedDB، الدور، التخزين الدائم، وحماية HTTP. Firebase الحي وجهاز iCall الفعلي لم يُستخدما في الاختبار.

## تشغيل استقبال المكالمات المحلي
- `npm run dev` يستمع على `127.0.0.1:9005`؛ `POST /api/calls` يقبل `{eventId, source, phone, timestamp, line?}`، مع timestamp بصيغة ISO ومنطقة زمنية.
- المصادر: `WHATSAPP`, `LANDLINE_ICALL`, `MANUAL`, `CUSTOMER_APP`.
- حماية POST: `Authorization: Bearer <token>` وJSON حتى 4096 بايت. الرمز يُولّد تلقائيًا في `.dispatchpro-local/call-token`، أو يُضبط بالخادم عبر `DISPATCHPRO_CALL_TOKEN` (32 حرفًا فأكثر). لا يُرسل للواجهة ولا يُحفظ في Git.
- سجل المكالمات داخل `.dispatchpro-local/calls`؛ تكرار eventId بنفس البيانات يعيد 200 دون حدث جديد، واختلاف البيانات لنفس eventId يعيد 409. مكالمة جديدة تستخدم eventId جديدًا حتى لو تكرر الرقم.
- `scripts/send-call.mjs` يصدر `sendCall(event)` لربطه بالـadapter السابق. تجربة محلية: `npm run call:send -- WHATSAPP 0000`؛ الوسائط الاختيارية: eventId، line، timestamp. أعد نفس الحدث كاملًا عند retry.
- لوحة المكتب تقرأ سجل الأحداث كل ثانية وتحوّل WHATSAPP وLANDLINE_ICALL تلقائيًا إلى طلبات عبر `ReceptionBackend.receiveCall`. آخر مكالمة للمعلومات فقط؛ لا نقر لإنشاء طلب. MANUAL وCUSTOMER_APP لا ينشئان طلبًا من سجل المكالمات.
- الطلب التلقائي يستخدم `pending` مع `receptionPending=true`؛ يظهر أعلى الجدول حتى عند تصفية اليوم/البحث، ولا يمكن تعيينه قبل حفظ النموذج بعنوان صالح. تبقى مدخلات أي نموذج مفتوح كما هي.
- معرّف الطلب مشتق من SHA-256 لـeventId، والحفظ create-only داخل معاملة الترقيم: إعادة التشغيل والتبويبات المتعددة لا تكرر الطلب ولا تمس تعديلات الموظف. الأرقام المتطابقة مع eventId جديد تنتج طلبًا جديدًا.
- البحث في الزبائن المحليين `customers` أو حسابات Firebase الحالية `users` بواسطة `phoneNumber`/`phone` بعد توحيد التنسيق المحلي والدولي؛ `name`/`displayName` و`defaultAddress` اختياريان. لا يُفترض عنوان مجهول ولا تُرسل إحداثيات زبون مختلقة.
- يجب أن تكون لوحة المكتب مفتوحة ومسجلة الدخول لإنشاء Ride في IndexedDB/Firebase؛ أثناء إغلاقها تُحفظ الأحداث بالخادم وتُستدرك تلقائيًا عند فتحها. الاستقبال بالخادم مستقل، ولا تضيع المكالمات المتتابعة بين استعلامين. تشغيل الإنشاء دون متصفح يتطلب worker الخلفية في المرحلة التالية.
- endpoint معطّل في الإنتاج افتراضيًا. للاختبار المحلي للبناء فقط: `DISPATCHPRO_LOCAL_CALLS_ENABLED=true` مع تشغيل الخادم على loopback؛ لا تنشر هذا المسار خلف proxy عام.
- يلزم حفظ مجلد البيانات المحلي عند نقل جهاز المكتب. `DISPATCHPRO_LOCAL_DATA_DIR` اختياري لتحديد موقعه أو لعزل بيانات الاختبار.
