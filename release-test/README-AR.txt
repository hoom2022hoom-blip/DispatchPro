LANDLINE iCALL — Caller Number + Ethernet capture + DEBUG

شغّل DispatchPro-Icall-Test.exe بعد نقل مجلد release-test كاملًا.
انتظر CAPTURE READY بجانب كرت Ethernet ثم اتصل بالخط الأرضي.
يظهر Caller Number أعلى النافذة مع Timestamp وSource IP مرة واحدة لكل جلسة رنين.
تبقى كل الحزم الخام في النافذة وفي icall-raw.log؛ تكرار الأرقام في السجل الخام طبيعي.

Parser هذه النسخة:
- يستفيد من حقلَي هاتف متطابقين قرب نهاية payload، ولا يبحث عشوائيًا في أرقام التاريخ والوقت.
- يقبل 05 مع 8 أرقام إضافية، أو 09 مع 7 أرقام إضافية، مع شرطات ومسافات اختيارية.
- يزيل الشرطات والمسافات ويشترط تطابق الحقلين بعد التطبيع.
- يدعم padding والفواصل البسيطة وNUL وCR/LF وETX بعد الحقلين.
- يرفض الحقول المختلفة أو الرقم الوحيد أو البيانات المبتورة والمجزأة.
- الأمثلة 056-898-4084 / 0568984084 و092315136 / 092315136 مغطاة بالاختبار.
- لم تُقدّم الحزم الأصلية الكاملة؛ الاختبارات تستخدم أغلفة اصطناعية حول الرقمين المبلغ عنهما. حدود الحقول ومعرّف المكالمة لم يُؤكدا من HEX حقيقي بعد.
- إن ظهر PARSER: no matching repeated phone fields فاحتفظ بـicall-raw.log لإضافة الصيغة الحقيقية، دون تخمين رقم من رأس الحزمة.

منع التكرار:
- حقلان في الحزمة أو نسخ من Npcap وUDP أو عدة حزم أثناء الرنين تنتج حدثًا واحدًا.
- الحالة محفوظة عبر إعادة التشغيل. كل حزمة مكررة تمدد مهلة الصمت.
- بعد 30 ثانية بلا حزم مطابقة، نفس الرقم ينشئ حدثًا جديدًا.
- إلى أن تتوفر حدود بداية/نهاية المكالمة ورقم الخط، مكالمتان سريعتان بنفس الرقم خلال هذه المهلة (حتى على خطين مختلفين) قد تندمجان، وفجوة حزم أطول قد تقسّم الرنين الواحد.

Call Integration:
- يظهر الرقم فور حفظ الحدث محليًا، حتى عند تعطل HTTP.
- يمر الحدث LANDLINE_ICALL عبر sendCall الحالي إلى POST http://127.0.0.1:9005/api/calls.
- النسخة تشغّل route ومخزن Call Integration الحاليين إن كان المنفذ متاحًا؛ لا تشغّل مستقبِل iCall القديم أو WhatsApp.
- الإعادة كل 5 ثوانٍ بنفس eventId والبيانات. الطابور محفوظ في data\caller.
- الافتراضي: أحداث نسخة الاختبار في data\calls ورمزها في data\call-token.
- للربط بنسخة DispatchPro تعمل بالفعل، اضبط dataDirectory في integration-config.json إلى مجلد بيانات Call Integration الخاص بها (الذي يحتوي call-token)، ثم أعد تشغيل الاختبار. هذا مسار ملفات فقط ولا يغيّر الشبكة.
- إذا كان المنفذ مشغولًا تُستخدم الخدمة الموجودة؛ اختلاف مجلد الرمز سيظهر كخطأ مصادقة مع إبقاء الحدث في طابور الإعادة.
- إنشاء الطلب في لوحة DispatchPro يعتمد على فتح اللوحة وقراءتها مخزن المكالمات نفسه؛ ظهور الرقم في الاختبار لا يعني وحده إنشاء طلب.

الالتقاط والمتطلبات:
- Npcap مطلوب للالتقاط المباشر من Ethernet؛ قد يتطلب التشغيل كمسؤول. https://npcap.com/
- فلتر Npcap: udp port 3520 and src host 192.168.0.90، ويقبل وجهة broadcast 255.255.255.255.
- UDP fallback باقٍ على 3520 لجميع المصادر في DEBUG؛ أحداث caller تُقبل من 192.168.0.90 فقط.
- Windows 10/11 x64 مع .NET Framework 4.x؛ Node.js مضمّن.
- لا تغيير IP أو DNS أو Gateway أو Firewall، ولا تفعيل promiscuous mode.
- لا تعديل أو تشغيل لتكامل WhatsApp. التعديلات محصورة في release-test.

نتائج التحقق:
- بناء EXE واختبارات Ethernet و7 اختبارات parser/UDP/dedup/retry/Call Integration ناجحة.
- اختبار عملية Node المضمّنة عبر نفس رسائل IPC المستخدمة من Npcap: خمس نسخ من payload -> رسالة Caller واحدة -> حدث واحد محفوظ عبر endpoint الحقيقي المضمّن.
- لا يوجد Npcap أو جهاز iCall في بيئة البناء؛ يلزم التأكد من مطابقة parser للحزمة الحقيقية على كمبيوتر المكتب.
