# Driver continuation — 2026-09-29

The pre-existing Android 0.1.1 APK and all completed driver/backend files are retained unchanged. No Flutter structure was found. The existing React dashboard and `src/lib/driver-api.ts` are the shared source of truth for login, availability, assignments, accept/reject, private customer details after accept, pickup/destination, Arrived/Start/Complete and history.

This portable web target bundles that same source for Android and iPhone browsers. Run `node driver-mobile/build.mjs` from the repository root. Serve the resulting `public/driver-mobile/` files through the existing Next.js HTTPS deployment and open `/driver-mobile/index.html`. The existing same-origin `/api/reception` proxy and its `DISPATCHPRO_API_URL` configuration are required. Opening the HTML from disk or a standalone static host without that proxy is insufficient. No backend changes or migrations are needed.

`runtime.ts` defines the injected fetch and notification provider contract. `android-platform.ts` adapts the already-implemented Android bridge. The web entry uses browser transport and notifications, including safe fallback to the existing in-app feed on iOS. A future iOS native host supplies these same interfaces before mounting the dashboard; no ride logic or backend replacement is necessary. No iOS native bridge or signed IPA is claimed here.

The web target keeps tokens in the existing in-memory session and uses existing no-store API calls. It refreshes state after browser resume. There is no added offline cache, write replay, background polling, Push/FCM/APNs service, or guaranteed delivery while closed. Notification permission is requested only by the existing explicit button. iOS system notification support depends on the host/browser; the in-app feed remains the baseline.

Remaining device acceptance: serve through the existing HTTPS frontend, test an existing driver account on Android and iPhone through availability, receive, reject, accept, customer details, Arrived, Start, Complete, history, loss of connectivity and resume. The existing Android APK was previously built/signed; no phone installation or iPhone runtime verification has been established by this continuation. Native iOS packaging/signing requires a subsequent macOS/Xcode stage if an App Store/IPA deliverable is required.
